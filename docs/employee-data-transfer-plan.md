状态：待用户另行下令实施；本次仅制定计划，不实现功能、不部署、不操作正式资料。

## 1. 目标与边界

超级管理员后台新增「資料遷移」，包含「導出」「導入」「紀錄」。旧站导出加密分卷，新站直接选择文件、输入原口令，浏览器自动解密、检查，再经对应与确认执行导入，无需另装解密软件。

必须保持本次选择范围内的员工登录、钱包及待处理提款、每日订单明细与累计订单数、聊天与媒体、通知、实名、登录和工时资料一致。共享配置由新站配置；不能承诺整站逐字节复制或任何配置下的提款结果都相同。

只允许 super_admin，页面隐藏不能代替服务端权限校验。所有正式环境迁移、Edge Function 部署、Storage/权限调整、定时任务调整、封存或修改正式资料，分别说明影响并取得确认。推送不等于前端部署。

不做：两站持续同步、自动定时备份、一键全量撤销、共享配置整体迁移、真实订单金额/交易内容/产品历史迁移、把新旧同名员工的钱包和记录相加。

## 2. 已确认的业务决定

1. 完整员工备份加密，包含密码校验资料，绝不导出明文密码；提供独立解密工具仅作应急备用。
2. 待处理提款一起迁移，保持待处理和冻结金额，切站后只在新站继续处理同一笔提款。
3. 不迁移处理中订单，只报告；迁移已完成订单的精简记录，支撑每日明细、累计订单数及相关提款判断，不带真实金额、订单号、交易号、产品和内容。
4. 同用户名员工以导入资料为准：覆盖前独立备份并校验，再走现有封存员工流程，再导入；不直接覆盖原记录，不合并钱包。
5. 相同聊天角色合并历史，不多建一个重复角色；存在歧义必须人工决定。
6. 导出和导入都提供实际处理进度，不模拟百分比；文件传完不代表资料核对完成。
7. 未完整核对的导入员工保持停用；切站时是否统一放行，还必须满足整站维护窗口条件。

## 5. 对应、替换与合并规则

### 5.1 员工

- 用户名与现有登录匹配规则保持一致，区分大小写，不自行新增大小写折叠或重命名规则；先测试输入去空格与历史存量用户名。
- 同用户名、不同 ID：展示新站员工概况，逐人确认；先备份并实际校验，再封存，再重新干跑。
- 同 ID、同用户名：正常重复包跳过并报告；只有确实属于该迁移任务的未完成账号可续传。
- 同 ID、不同用户名，用户名占管理员，员工号被不同用户名占用：跳过并写原因，不自动改号。
- 管理员按用户名预选并允许手动对应；不对应紧急管理员或不符合业务范围的账号。每员工最多一个派单分组；名称相同但多候选必须选择。
- 封存调用 `archive_employee_without_media`；有媒体/通知证据时沿用 `mutateAuditedContent('employee_delete', ...)`，不新增可绕过留证的删除接口。
- 备份和封存之间再次确认目标资料未变化。全站只允许一个活跃迁移任务，替换前备份任务要先结束，不能被导入锁卡住。
- 备份有效不等于有一键恢复；同站恢复与 UUID 冲突按第 3 节的阻断要求处理。

### 5.2 聊天角色

范围：映射后的同一管理员 + 相同 `aaa_service` / `ccc_service`。

1. 编号和名称都相同：自动合并；仅名称相同且候选唯一：自动合并并标依据。
2. 同名多候选，或仅编号相同但名称不同：必须手选合并目标或新建。
3. 无候选则新建；显示编号被其他角色占用则生成新编号并报告；多个旧角色合并到一个目标需额外确认。
4. 已有目标角色的名称、头像、设置不覆盖。其指定员工可见范围的调整要显式确认、只加入成功导入的对应员工，并审计。
5. 新建角色只使用实际导入员工映射后的指定名单。若原角色有限制而过滤后为空，不能把空名单误当“对所有员工开放”；保持限制/暂不启用直到名单确定。
6. 聊天消息按 ID 和内容归属检查后去重。工单按角色/员工/状态槽位对应；工单编号冲突另生成并记录。备注冲突保留新站；多旧备注合一时展示取舍，原始内容留在备份。
7. 富卡先冻结并迁移实际 HTML；媒体重写后重新计算目标内容哈希，保留源→目标快照映射。不把既有 MD5 去重键当作安全认证；同哈希复用仍比较实际内容，文件完整性使用 SHA-256。
8. 自动消息按角色、类型、标题、副标题、正文对应，新站内容完全相同才标记已发送；对应不上单独报告，提示可能补发。链接重写导致的特征变化必须统一口径。
9. 同名员工被替换后，其旧新账号并不是同一个员工 ID；新站原员工聊天仍归封存账号。相同角色可以共用，但不将被封存员工的聊天混进新账号。

## 6. 资金写入与隔离

### 6.1 原子边界

按员工暂存账号、钱包、基准、账本、流水、提款及相关小表，再在一个事务内验证并提交；资金校验失败回滚该员工核心。订单、通知、活动和聊天分批，不承诺整套迁移跨请求自动回滚。

账号首先停用，所有依赖及文件完成后才能按原状态恢复。暂停、取消或失败不能自动清空已经提交的资料；已经合并到共享角色的内容也不能直接整段删除作为回滚。

### 6.2 资金核对

以现有 `reconcile_wallet_from_ledger` 的实际定义为准：

- 冻结金额 = 待处理提款合计。
- 可用 + 冻结 = 基准可用 + 基准冻结 + 基准游标之后的账本增量。
- 总收入 = 基准收入 + 基准游标之后的收入增量。
- 对账后资金零非预期修正；pending 数量、金额与来源一致。

金额使用数据库 numeric 和稳定十进制表示，不用浏览器浮点累加作为资金最终判定。基准/账本缺失或源站资金已不一致时，不自动“修平”，列出差异并阻断相关员工。

账本按旧编号顺序申请目标序列，基准游标换算成旧编号 ≤ 旧游标的最后一条对应新编号；没有为 0。测试目标已有账本、序列间隙、游标超界及操作唯一键冲突。

### 6.3 触发器与维护窗口

仅旁路经过审核的副作用触发器，保留外键、组隔离、封存保护和媒体/富卡保护。事务内关闭、精确恢复，审核定义及状态而不仅名称；异常、超时、锁冲突都验证不会残留关闭状态。禁止未经确认改用全局复制模式或绕过所有保护。

关闭触发器会取表锁，不承诺无感在线迁移。核对 postgres 权限、PostgREST 事件/缓存、实际语句超时、请求大小、锁超时和各表查询索引。验证 PGlite 不覆盖的真实 PostgreSQL 并发与 Storage 行为时使用独立隔离环境，涉及创建服务与费用先取得确认。

停用员工不能阻止全部 cron、其他管理员和直接 API 写入。正式切站必须明确：旧站停止相关写入、新站维护窗口内阻止业务写入、哪些自动任务需暂停、操作者和恢复步骤；任何正式设置改变均另行确认。不能仅关闭前端页面当作数据库隔离。新站加入自动化方案要在导入核对后进行，并验证加入基线不会补发历史奖励。

## 7. 加密分卷与媒体

### 7.1 文件格式

- 每卷 `.edx`，版本化容器，内层 ZIP 流：manifest、分表 NDJSON、media 和必要对应元数据。
- 外层 AES-256-GCM，约 1 MiB 分块；PBKDF2-SHA256 600,000 次、每卷随机盐、唯一 nonce，认证关联容器/卷/块编号和末块信息。检测错误口令、修改、截断、重排、重复块、跨包换卷和缺卷。
- 同一套包有随机 export ID，卷编号和依赖清单；约 150 MB 只是分卷目标。大员工可跨卷，必需卷不全不能恢复启用。避免把所有卷和明文资料同时放入内存。
- 每个数据文件/媒体及每卷 SHA-256；清单含选择范围、格式与结构版本、源站身份、导出时间、保留配置、员工各类数量/摘要以及对应身份。业务清单置于认证加密范围内。
- 口令至少 14 位，推荐一键生成 24 位随机口令并二次确认。口令不写日志或浏览器持久存储，不发往数据库；管理员二次认证密码是另一件事，仅提交到受保护认证接口。
- 索引与普通报告不暴露密码校验、证件、聊天正文或逐员工资金明细。需要详细的运营报告时一并加密或在登录后查看。
- Chrome/Edge 支持时流式写入磁盘；不支持时给出分卷内存限制和明确提示。下载动作触发不能冒充磁盘保存成功，替换前备份要求重新读取校验或有可验证的保存流程。
- 提供 Node 20 独立解密脚本，正常网页导入无需使用它。对比网页和独立脚本双向兼容。

### 7.2 媒体流程

提取结构化 URL 和富文本里的本站媒体，去重后下载并计算哈希；覆盖聊天、通知、富卡、头像、证件和内嵌资源，验证相对 URL、查询参数、签名 URL 和 data URL 的明确处理规则。虚拟头像键不是文件，不应下载。

目标文件同路径同 SHA-256 才复用；冲突则安全改名并保存映射，绝不覆盖新站已有不同内容。改写所有引用之后重新核对快照和内容摘要。上传默认有限并发（初始 4，可由测试调整），单文件失败单独显示，重试先确认目标对象状态。

管理员是自建会话，现有 anon 上传工具不能证明获得超级管理员授权。逐桶核对公开/私有、路径前缀、大小、MIME、CORS 和签名方式；必要时提出绑定任务、路径、大小和短时效的受控签名/代理能力，明确服务端部署边界。不在浏览器放 service_role、不放宽全桶权限、不把私有文件改公开。

只允许已知源站及白名单桶/安全路径，不抓任意外站 URL。导入文件按不可信输入处理：限制解压体积、条目数、单条大小与路径，不允许穿越、重复覆盖、HTML 执行或外链请求。媒体改写后仍须净化显示。现有公开证件桶等权限问题另列整改，文件加密不解决在线权限问题。

## 8. 真实进度与任务恢复

### 8.1 界面

深色繁体中文、明确 UTC+8；顶部任务阶段、总体员工进度，下面当前员工/类别/批次、记录数量、文件数量/字节、耗时、估算剩余时间、最后确认时间；成功/跳过/失败/待处理分开。

示意（非真实运行）：已核对员工 23/100；当前员工 A；聊天写入 8,000/20,000；媒体已确认 300/450；状态「等待伺服器確認」。

导出阶段：预检 → 读取资料 → 下载媒体 → 打包加密/写盘 → 校验分卷 → 完成。
导入阶段：解密校验 → 兼容/干跑 → 对应确认 → 覆盖前备份与封存 → 文件上传 → 资金核心 → 历史与聊天 → 核对 → 恢复状态。

### 8.2 真实计数

- 总量未知时显示“正在统计”和实际数量，不给虚构百分比。
- XHR 发出字节与服务端确认写入是两种状态；传输 100% 时仍可能等待确认。
- 数据库提交一批后，持久化该批回执及 checkpoint，再增加确认数量；批次重试不重复计数。
- 以任务 ID、包哈希、员工 ID、阶段、块号、块哈希作为请求身份；同身份不同内容拒绝。金额和员工状态以数据库为准。
- 进度读取接口校验管理员、任务归属；不假设 private 表有 Realtime。使用带节流的受保护查询，浏览器本地媒体进度与服务端提交进度分开。
- 任务 finish 由服务端根据固化清单、实际回执和核对结果判断。全部成功、结束但有失败、取消、等待恢复明确区分，不能只返回 success=true。

### 8.3 暂停、取消与中断

- 暂停在当前安全批次确认后生效；不会假装撤销已发送事务。
- 超时结果不明时显示“结果待确认”，查询已提交状态再决定后续，不自动重放写请求。
- 取消只停止后续处理，保留报告与已完成数据；待完成员工继续停用。
- 切换后台导航保留组件与任务状态；关闭浏览器不承诺后台继续运行，离开时提示，长任务可请求屏幕常亮。
- 刷新/断线/重新登录后从服务端确认检查点恢复，必要时重选文件和重输口令。会话与任务凭证过期有独立认证流程，旧凭证失效，原任务不可被别的包接管。
- 已完成卷和已确认员工无需重做；仅半成品输出卷可以作废后重新生成，界面不能将“读取完”算成“加密文件已保存”。
- 现有任务“2 分钟无活动就抛弃”的逻辑必须改为显式租约/心跳和接管规则；大文件/密码派生/手动暂停不能错误丢弃任务。

## 9. 用户操作流程

### 9.1 旧站导出

1. 明确本次是演练还是正式切站；正式导出安排停写窗口，保留源站和数据库备份。
2. 超管进入「資料遷移」→「導出」，选员工/管理员、类别与依赖。
3. 展示订单 processing、pending 提款、在线/工时、源站资金异常、文件估算与保留期；源资料异常不自动修改。
4. 设置并确认文件口令，再验证管理员密码；建立固定范围的任务，返回格式与身份。
5. 按游标读取，批次不超过 5,000 行且受字节限制；对大员工拆分，文件有界并发。
6. 按实际回执更新进度；前后指纹发现变化则重导该员工，最多 3 次，仍变化不标成功。前后计数相同不能证明一致快照，正式验收以停写窗口/可证明快照为前提。
7. 关闭并校验分卷；导出完成报告、处理中订单提醒、pending 提款移交提醒、文件清单/哈希；口令另存。

### 9.2 新站导入

1. 先准备管理员、派单分组/提款条件和必要共享配置，并确认数据库迁移版本与 Edge Function。
2. 选加密文件、输口令，流式验证必需卷/内容/大小/格式；不写业务数据。
3. 检查不同站身份、表结构、审核过的触发器、保留期限、在线和维护状态；不兼容即停止，不能凭“格式版本相同”强行继续。
4. 对应管理员、分组、角色；所有歧义、多旧合一、受限可见范围和缺口有明确选择。
5. 干跑展示新建/跳过/替换/可续传及原因；再次核对 pending 提款金额和处理责任。
6. 对同名员工逐个确认，输入「確認導入員工資料」和管理员密码；完成覆盖前加密备份、实际校验、原站恢复可行性检查后才解锁封存。备份失败或资料变化则停止。
7. 沿用现有封存/稽核流程，失败项单独处理；重新干跑确认用户名和员工号释放，不一次执行所有剩余删除。
8. 开始/恢复导入任务，固化包清单与决定；先安全上传并改写角色依赖的文件，再按依赖创建/合并角色。
9. 按员工停用账号和资金核心原子写入 → 精简订单/通知/活动 → 卡片快照/聊天/工单/备注/已发记录 → 文件和资料完整核对。
10. 核对通过才恢复其原有启用状态；正式切站维护未结束时仍不能对外放行。未通过则保持停用、输出差异和可恢复检查点。
11. 输出结果，人工抽查原密码登录、每日明细、钱包/提款列表、聊天和证件；填写导入后待办。
12. 在确认数据和配置后再加入新站通知自动化方案，恢复约定任务和业务，旧站继续停止写入。

## 10. 分阶段实施与交付门槛

## 12. 测试与验收清单

### 12.1 数据和资金

- 同结构双库往返：账号和密码验证、资金核心、各类历史逐行/摘要一致；账本比较内容和顺序，允许编号重排；订单只比较保留字段。
- 日统计、总体统计、累计完成数、员工列表/详情、交易页、提款条件输出对比；新旧配置不同导致的差异明确报告，不能当资料损坏或保证仍一样。
- 导入不多写佣金、账本、收入、自动化奖励、非预期稽核/对账队列；手动与 cron 对账后零非预期修正。
- 冻结合计、账本游标边界、序列间隙、不同目标已有数据、无基准老账号、源资料不一致、精度和空值全部覆盖。
- 当天精简订单、时区跨日、失败佣金约束、停用占位产品、processing 不导入验证。

### 12.2 替换与聊天

- 同名：备份校验 → 封存 → 再干跑 → 导入；媒体/通知证据路径和封存保留均验证。对备份恢复不能只检查 ZIP 可打开，必须演练恢复身份/数据关联。
- 员工 ID/用户名/员工号/管理员冲突和同包重复、半途续传、不同包复用旧任务测试。
- 角色匹配全部分支、跨管理员/类型拒绝、多个源角色合一、目标属性不被覆盖、受限名单不扩大可见范围。
- 聊天同 ID 同内容幂等、异内容冲突；工单编号/槽位和批内冲突；备注取舍；新旧富卡/媒体重写/同哈希不同内容拒绝。
- 自动消息同内容对应、不对应补发提醒；加入通知方案基线不补发历史奖励。

### 12.3 文件、任务和权限

- 正确口令、错误口令、字节翻转、截断/追加/重排、缺卷/跨包、损坏清单、解压规模/路径攻击、外部链接和不安全 HTML。
- 同路径同内容复用、同大小不同内容改名、私有文件权限、签名过期、缺失媒体、超限类型、下载上传中断。
- 超时前提交/超时后提交/未提交三种结果；暂停、取消、关闭、会话和任务过期、重新认证、并发标签页、进度不重复累计、finish 不可伪造成功。
- 文件输出未落盘、内存上限、单个大员工跨卷、重选文件与续传匹配。
- 非超管、过期或撤销会话、伪造/串用任务令牌、写入范围外员工、未知列/表/触发器、跨任务回执均拒绝。
- 真实 PostgreSQL 锁、事务失败和原触发器状态恢复验证；不能靠 PGlite 替代云端行为。

### 12.4 界面与回归

在模拟后端中实际操作导出/导入向导、角色对应、替换、进度、错误和恢复；桌面 Chrome/Edge 为正式大规模迁移推荐，兼测窄屏及可用的 WebKit。环境不能测试时如实说明，正式账号只由用户或另行授权的演练使用，不索要明文密码。

实施后命令：`npm run typecheck`、`npm run lint`、`npm run build`；新增 `npm run test:employee-transfer`，并运行现有 `test:service-chat`、`test:audit-cleanup`、`test:work-session`。更改 Edge Function 时追加语法检查。每项记录真实通过/失败/未覆盖，不能只写“测试完成”。

## 13. 正式部署、切站与失败处理

1. 用户下令实施后先完成 A–F，不把“开始实施”视为修改正式库或迁移真实员工的授权。
2. 上线前只读核对目标库实际结构、权限、触发器定义及状态、迁移历史、存储桶、超时和 cron；本计划未执行这些正式检查。
3. 列出待部署 SQL/服务端/前端、影响、锁风险、备份与恢复办法，单独取得旧站数据库部署确认。新增迁移先行，前端在依赖可用后上线；前端由用户按现有部署流程发布。
4. 若需媒体服务、Storage 权限或正式 cron 改动，分别确认，不夹带在一般部署中。
5. 用测试/少量员工旧站导出，隔离新站导入，核对报告及浏览器实际页面。演练资料不得在之后的正式导入中因同 ID 被误判完成。
6. 新站准备管理员、分组及提款条件、角色/自动消息等共享配置；完整迁移回放有历史缺口时先补可重复的正式建库方案，不盲跑所有旧 SQL 并忽略失败。
7. 单独确认正式切站时间、旧站停写、新站维护、pending 提款交接责任、原站备份保留和定时任务暂停/恢复清单；之后才允许正式导出/封存/导入。
8. 完成导入，逐员工自动核对、人工抽查、确认新站任务/自动化基线，才恢复业务；旧站保持停写，避免双站登录、双站做单和重复打款。
9. 保留加密文件、口令、清单/报告、切站记录和旧站备份，保留多久由用户确认；不自动删源库或原站媒体。

失败处理：单员工核心事务失败回滚核心，其余分批失败保持停用并续传；批次结果不明先查状态；封存前失败不继续替换；封存后失败靠保留资料与经验证的恢复流程处理。已经对外开放新站并发生新交易后，不能简单切回旧站，必须先核对切站后变化。数据库 DROP 回滚仅移除迁移能力，不能等同撤销业务数据；审计和凭据/资料不可随意 DROP 丢失。

## 14. 实施前需明确的两项范围调整

这两项不在本次偷偷实现，下一次实施前先确认：

1. 当天精简订单展示：推荐最小修改员工订单展示，标明历史导入并不把占位产品/金额当真实业务展示；保留原日期、佣金与统计。金额类统计不能伪装成与源站相同。若坚持完全不改员工端，则须接受明确展示差异，不能同时承诺“完全看不到占位值”。
2. 覆盖前备份恢复：推荐实施受控、可演练的恢复路径，解决同站检查、封存 UUID 和关联资料冲突；这不是取消全部保护或一键撤销迁移。若暂不纳入，必须在替换确认前明确只保留追溯和受限恢复能力，不承诺一键导回。

最终放行标准：必需数据与文件齐全、资金公式与业务统计核对通过、无未解释冲突、失败账号不放行、真实进度及结果一致、恢复限制已说明并经用户确认。

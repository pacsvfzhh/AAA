新网站迁移操作步骤（数据库已直接转移版）

适用情况：旧数据库已经通过你使用的“数据库直接转移”方式复制到新 Supabase 项目。本手册不再讲 CLI、pg_dump 或重新搬数据库，只说明转移后要做的检查、文件处理和上线准备。

当前已知状态：你提供的 04 报告显示，目标项目 galqpmfpwqxitzeqzdkd.supabase.co 的公告链接已切换 361 处，旧地址残留为 0。04 还不能证明文件字节实际可读取；现在不要重跑 04，下一步是用 03 只检查。

============================================================
第 1 阶段：确认新旧项目
============================================================

1. 登录 Supabase Dashboard。
2. 分别确认旧项目和新项目的项目名称、URL、项目 ref。
3. 之后运行 SQL 时，每次先看 Dashboard 当前项目名称，避免把 04 在旧项目运行。
4. 新旧网站不要同时让员工提交订单、处理提款或编辑相同资料。
5. 不要删除旧项目；确认新站稳定后再决定旧项目的处理方式。

安全提醒：数据库密码和 service_role／Secret key 不要发在聊天、截图、网页代码或 Vercel 的 VITE_* 环境变量中。

============================================================
第 2 阶段：运行 01 结构健康检查
============================================================

文件：supabase/migration-check/01_structure_health_check.sql
用途：只读检查目标数据库结构、权限、扩展、Storage 设置、Realtime、cron 和部分业务健康状态；不会改数据库，也不会搬数据。

操作：
1. 打开新项目的 Supabase Dashboard。
2. 左侧点 SQL Editor → New query。
3. 打开 01_structure_health_check.sql，把全文复制到查询框。
4. 点 Run，查看第一行“总结”和后续失败／警告／提示。
5. 先处理重要失败项；遇到不理解的结构差异，先暂停并核实，不要直接忽略。

注意：当前文件里的结构基线生成于 2026-10-26。如果旧数据库在这之后做过数据库结构更新，01 可能把新结构报成差异。应先按 SQL 文件开头说明，从当前旧库重新生成结构指纹并更新基线，再在新库运行。

01 不能检查 Edge Function 是否部署，也不能读取 Storage 文件的实际字节。

============================================================
第 3 阶段：运行 02 数据指纹对比
============================================================

文件：supabase/migration-check/02_data_fingerprint.sql
用途：只读比较旧、新数据库的逐表行数和内容指纹。

操作：
1. 在旧项目点 SQL Editor → New query，粘贴完整 02，点 Run。
2. 复制结果第一行“说明”栏以 v1; 开头的整段内容。
3. 在 02 文件副本中找到两个 $old$ 标记，把刚才复制的内容粘贴在它们中间。
4. 切换到新项目，点 SQL Editor → New query，粘贴更新后的整份 02 并点 Run。
5. 优先查看“核心业务”结果；“运行记录”类表可能因网站运行而变化，按说明判断。

顺序提醒：正常应在 03、04 之前做 02。你已经运行 04，所以公告正文链接已被改写；现在做 02 时 public.announcements.content 出现差异可能是预期结果，不要仅凭这一项判定数据库转移失败。

============================================================
第 4 阶段：检查新项目的 Supabase 设置
============================================================

在新项目 Dashboard 检查以下内容：

A. Storage 桶
1. 左侧点 Storage。
2. 核对来源项目的桶名称、公开／私有状态、文件大小限制、MIME 类型和策略。
3. 本项目常见桶包括 announcement-images、chat-images、content-audit-evidence（私有）、super-customer-avatars、template-images、verification-documents、website-icons。
4. 数据库里有 storage.objects 文件记录，不代表实际文件字节已复制。

B. Realtime
1. 左侧点 Database → Publications。
2. 打开 supabase_realtime。
3. 对照 01 的结果，核对网站需要实时刷新的表是否启用。

C. 扩展与 cron
1. 在 Database → Extensions 核对 01 所列扩展。
2. 查看 01 中的 cron 任务和最近运行情况；有失败先查明原因，不要盲目新增或关闭任务。
3. 新旧站不要同时处理相同业务。

============================================================
第 5 阶段：部署 content-audit Edge Function
============================================================

数据库直接转移不会自动部署 Edge Function。这个网站需要 content-audit，用于内容稽核留证、删除流程和私有附件读取。

Dashboard 操作：
1. 打开新项目 → 左侧 Edge Functions。
2. 点 Deploy a new function → Via Editor。
3. 使用项目最新的 supabase/functions/content-audit 源码上传／部署，函数名填写 content-audit。
4. 部署后打开该函数设置，确认 Verify JWT 关闭（verify_jwt=false），保存。
5. 打开函数 Logs，查看是否有启动错误。

本项目的 content-audit 使用自建管理员会话与数据库 RPC 校验身份；verify_jwt=false 是当前项目设计，不要擅自改成 true。目标项目的 SUPABASE_URL 和 SUPABASE_SERVICE_ROLE_KEY 由 Supabase 函数环境提供，不要把 service key 放进网站前端。

旧函数 process-orders 和 cleanup-dispatch 在项目文档中标记为旧函数，仓库没有对应源码且当前前端未调用；不要只因它们出现在旧项目列表就盲目部署。若旧项目另有实际在用的 Edge Functions 或 Database Webhooks，再逐项确认。

第 6 阶段：03 检查／复制公告图片和视频
============================================================

文件：supabase/migration-check/03_copy_storage_files.html
它是本地网页工具，不是 SQL。它只处理公告正文引用的媒体，不搬整个 Storage，也不迁移聊天附件、头像、实名文件或私有稽核附件。

由于你已经运行 04，现在的操作是“只检查，不复制”：
1. 用桌面版 Chrome 或 Edge 打开最新版 03_copy_storage_files.html。
2. 选择“直接复制”。
3. 来源地址和目标地址沿用你此前复制时的旧项目、新项目地址；目标应是 galqpmfpwqxitzeqzdkd.supabase.co。
4. 填写工具要求的来源及目标 service_role／Secret key。不要截图或分享密钥。

6. 确认待复制／待处理为 0、检查异常为 0、没有失败或中途停止；下载检查报告留档。
7. 打开新网站抽查多条公告里的图片、视频、封面是否显示／播放。

检查有异常时先看报告中的文件路径和原因，处理后再跑 03 只检查。不要为让报告变绿而手动伪造文件或跳过问题。
